Memory

Durable memory is untrusted data. The Python controller is the only process that reads or writes the canonical store. A skill is a client. A loopback service is stricter because the files never have to be opened by an agent.

Layout

Agents/Memory/
├── memory.md              # Contract for agents
├── schema.md              # Structured store
├── memory_ctl.py          # CLI entry
├── installer/
│   └── install_memory.py  # macOS + Windows
└── controller/            # Auth, validator, store, service

The live store is the directory that contains the MEMORY.md path in Settings/CONFIG.md. Installer sets owner-only permissions, writes hashed credentials, and migrates an existing markdown file into store.json.

Install

The main hub installer (Agents/Setup/scripts/setup.sh) asks whether to install durable memory on this machine. Yes runs this installer. No leaves it for later.

You can still run it on its own from the hub root:

python3 Agents/Memory/installer/install_memory.py

On Windows:

py -3 Agents\Memory\installer\install_memory.py

Optional macOS service:

python3 Agents/Memory/installer/install_memory.py --source /path/to/old/MEMORY.md
python3 Agents/Memory/installer/install_memory.py --launchd
launchctl load ~/Library/LaunchAgents/dev.gemlarin.memory-controller.plist

Tokens live in the OS secret store (macOS Keychain, Windows Credential Manager). Do not paste them into chat. Do not write them to user-config.md. Set MEMORY_AGENT_ID only; the CLI loads the token.

Flow

  1. Agent authenticates (MEMORY_AGENT_ID; CLI loads the token from the OS store).
  2. Controller checks permissions.
  3. Validator rejects secrets, PII, and malformed entries.
  4. Proposal sits in Proposals/ until Memory Steward approves.
  5. Controller commits to store.json, renders MEMORY.md, appends Audit/audit.jsonl.

Same-user file mode 600 does not stop Cursor from reading a path it already knows. The rules and CLI are the process boundary; a dedicated OS user would be stronger and is not in this install.
